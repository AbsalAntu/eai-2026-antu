# ADR-006 — Temporal workflow with classified activity failures instead of a hand-rolled saga store

**Status:** accepted
**Date:** 2026-11-10

## Context

I killed the PA6 orchestrator while shipping was slow (2000 ms). The client got no answer. After `docker start`, I sent the same request with the same Idempotency-Key. The answer was `409 idempotency_conflict`, "A request with this Idempotency-Key is still in progress".

The cause is in my PA6 handler. It writes the key's record with state `in_progress` and httpStatus 202 before the first call. It updates the record only when the saga ends. The crash fell in between, so the record stays `in_progress` for ever. The payment may already be taken, the order never finishes, and nothing records which steps ran.

I ran the same kill in PA7. I started a checkout with slow shipping, then ran `docker kill pa7-worker` and `docker start pa7-worker`. The workflow still returned 200 `completed`. The payment mock logged `authorize` once for the order. The shipping mock logged `create` twice for the same order, at 23:30:50.679 and 23:31:00.147. The trace shows shipping at 11657 ms.

The second decision was which failures Temporal may retry. A declined payment will be declined again. A 5xx or a missing answer might succeed next time.

## Decision

The boundary sits at the network. Every HTTP call is an activity in `activities/index.ts`. The helper `post` returns on 2xx. On a 4xx it throws `ApplicationFailure.nonRetryable` with the mock's `code` from the body. On a 5xx or no answer it throws `ApplicationFailure.retryable`.

The workflow in `workflows/checkout.ts` does no I/O. `proxyActivities` sets `startToCloseTimeout` 2500 ms, `maximumAttempts` 3, `initialInterval` 200 ms and `backoffCoefficient` 2. I kept PA6's 2500 ms per call. Three attempts bound a stuck call to about 8 seconds.

`computeAmount` sums whole cents with `toCents` and formats once. `runStep` runs one activity and records one trace entry. A `TimeoutFailure` becomes code `timeout`. An `ApplicationFailure` gives its `type` as the code.

On a failure, the workflow runs `releaseInventory`, then `refundPayment`, for the steps that completed. If an undo fails, the result is `failed` with `compensation_failed`. The workflow returns a `CheckoutResult` for every outcome and never throws.

## Alternatives considered

**Keep the PA6 orchestrator and add a recovery job on startup.** This is the real alternative. The job would find `in_progress` records and finish or undo them. PA6 does not save which steps completed, so I would first have to persist every step's result before the next call. Then I would need a rule for re-running or compensating each step. That is a second copy of what Temporal's history already does.

**Retry every failure and let compensation sort it out.** A declined payment would be tried three times, and the test counts attempts. It also delays a refusal that cannot change.

**One activity for the whole saga.** A retry would then repeat the payment as well as the failed step. It also hides the steps from the history.

## Consequences

Easier: a crash mid-saga no longer strands a key. The history knows which steps finished, and the worker carries on from there.

Harder: activities run at least once. In my crash test shipping ran twice. If `authorizePayment` had been the step in flight, the customer could be charged twice. No engine can prevent this, because it cannot know whether a call that died reached the service. The payment service must treat the same `orderId` as the same charge.

A workflow that is running when I deploy changed code is replayed against the new code. If the step order differs, replay fails. Changing a live workflow needs versioning.

Accepted cost: I now run and watch a Temporal server and a worker. The stack went from five containers to seven. A call that keeps timing out holds a checkout for about 8 seconds before it fails.

## What the engine took over

- **Timeouts.** PA6 wrapped every call in its own timeout and mapped the abort to "timeout" by hand in `callStep`. In PA7 `startToCloseTimeout` fails the attempt and the workflow sees a `TimeoutFailure`.
- **Idempotency records.** PA6 kept `idempotency-store.json` and wrote an `in_progress` record in `POST /checkout`. In PA7 the api starts the workflow with the Idempotency-Key as its id, and Temporal refuses a second workflow with the same id.
- **Where was I.** PA6 kept the `completed` list in memory, so a crash lost it. In PA7 the workflow history holds every step's result, and replay rebuilds that list.
- **Saga state on disk.** PA6 wrote `saga-store.json` itself. In PA7 Temporal's history is the source of truth, and `api/data/` is only an audit mirror.
