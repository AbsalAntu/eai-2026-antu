# ADR-001 — Durable queue, publisher confirms, manual ack, and correlationId propagation for order publishing

**Status:** accepted
**Date:** 2026-09-22

## Context

This assignment forces four separate decisions, each of which only matters at the exact moment the broker or consumer dies mid-flight.

**Durable queue.** `channel.assertQueue("pa2.orders", { durable: true })` is what lets a message survive `docker restart pa2-rabbitmq`. Without `durable: true`, RabbitMQ drops the queue itself on restart — not just its contents — so every later demonstration in this assignment silently breaks before you even get to publish anything.

**Publisher confirms.** A `POST /publish` that calls `channel.publish()` and immediately returns `202` looks correct — it passes every contract test, and the message really does get sent. The problem only shows up when the broker dies before that message reaches disk. I confirmed this directly with `04-publisher-confirms-prevents-loss.test.ts`: publishing a batch of 5 messages with `X-Publish-Mode: fire-and-forget`, then killing `pa2-rabbitmq` with `SIGKILL` (not a graceful `docker restart` — the test deliberately avoids that, since a graceful shutdown gives RabbitMQ time to flush even non-persistent messages to disk first, which would turn the test into a coin-flip), left fewer than 5 of those messages recoverable, even though the HTTP client had already received `202` for all 5. The same batch, published in the default confirmed mode, survived the identical kill with all 5 intact.

**Manual ack.** `handleMessage` writes the message to `received.jsonl` with `appendFileSync` before calling `channel.ack(msg)`. If the ack happened first, a consumer crash between the two lines would leave RabbitMQ believing the message was delivered — it's gone from the queue — while it was never actually written anywhere. That failure is invisible from the broker's side; only ack-after-write makes it recoverable (the message gets redelivered on reconnect).

**correlationId propagation.** It isn't enough for the id to show up somewhere in a log line — it has to be the same value at every hop: HTTP header (`X-Correlation-Id`) → validated in `handlePublish` → set as an AMQP message property in `publishMessage` (`msg.properties.correlationId`, not embedded in the JSON body) → read back out the same way in `handleMessage` → written into the `received.jsonl` line. Putting it in the body instead would work by accident for this consumer, but would break for any consumer that doesn't happen to parse the body the same way.

## Decision

**`connectProducerChannel(url, queueName)`** opens a confirm channel — `connection.createConfirmChannel()`, not the plain `createChannel()` — and asserts the queue with `{ durable: true }`. The confirm channel is what gives `publishMessage` a callback to wait on later.

**`publishMessage(channel, queueName, payload, options)`** builds the publish options as `{ correlationId: options.correlationId, persistent: options.mode === "confirmed" }` — so the persistent flag and the confirmed mode are tied together, not independent choices. In `"fire-and-forget"` mode it calls `channel.publish()` and returns immediately. In `"confirmed"` mode (the default) it wraps the same `channel.publish()` call in a `Promise` that only resolves once the broker's confirm callback fires — so `handlePublish` cannot send `202` to the HTTP caller until the message is actually durably queued.

**`connectConsumerChannel(url, queueName)`** opens a plain channel (no confirms needed on the consuming side) on the same queue name and durability setting as the producer, and sets `channel.prefetch(10)` to cap how many unacked messages RabbitMQ will hand this consumer at once — necessary because acking is manual.

**`handleMessage(channel, msg)`** reads `msg.properties.correlationId`, parses the message body, appends a JSON line (correlationId, payload, and a `receivedAt` timestamp) to `received.jsonl` via `appendFileSync`, and only then calls `channel.ack(msg)` — the ack is the last line in the function, strictly after the write completes. `msg.properties.correlationId` is trusted as-is here; it was already validated once, upstream, when it entered the system through `handlePublish`'s regex check on the HTTP header — it isn't re-validated a second time on the consumer side.

## Alternatives considered

**`channel.publish()` then `202` immediately, with no confirm callback.** This is the version most naive amqplib code actually writes, and it's dangerously close to correct: it publishes a real message, `channel.publish()` even returns a boolean, and it passes every contract test in this assignment except one. The boolean only tells you the local write buffer accepted the call — it says nothing about whether the broker has durably received the message. `04-publisher-confirms-prevents-loss.test.ts` exists specifically to catch this: it's the difference between "I called publish" and "the broker actually has it," and no amount of manual testing that doesn't include a real broker kill would surface the gap.

**Acking before the write to `received.jsonl`, instead of after.** This ordering is easy to get backwards because it doesn't fail any test that doesn't specifically crash the consumer mid-write. But it creates a window where a process crash between the ack and the write loses the message permanently — RabbitMQ has already removed it from the queue, believing it delivered, while it was never persisted anywhere. Acking last means the worst case is a duplicate delivery on reconnect, not silent loss.

**Using the message body for `correlationId` instead of the AMQP `correlationId` property.** This would have worked for this specific consumer, since it's the only thing reading the queue — but it conflates application data with message metadata, and any other consumer or tooling (the RabbitMQ management UI, for instance, which surfaces `correlationId` as a first-class message property) wouldn't see it without parsing the body first. Using the property is the interoperable choice, not just the "correct" one.

## Consequences

Confirmed publishing makes `POST /publish` slower — every request now waits on a round-trip confirm from the broker before returning `202`, instead of returning the instant the TCP write happens. Under high request volume this is a real throughput cost, traded deliberately for the guarantee that a `202` means something.

Manual ack with `prefetch(10)` means the consumer can fall behind under load, and the queue will back up rather than drop messages — `03-consumer-stopped-accumulates.test.ts` demonstrates exactly this (5 messages piling up while the consumer container was stopped). If the consumer stayed down or slow for an hour under steady traffic, queue depth would climb continuously, and RabbitMQ's own disk usage grows with it — nothing in this design bounds that, so a sufficiently long outage becomes a disk-space problem on the broker, not just a latency problem for the consumer.

Running two consumer instances against the same queue would work safely as-is — RabbitMQ round-robins deliveries between competing consumers, and each message only needs processing once — but this only holds because nothing here assumes ordering between messages; if order mattered, competing consumers would break it.

Nothing in `handleMessage` bounds the size of an incoming payload. A 100MB message body would be accepted by `JSON.parse` and held fully in memory before being written — there's no streaming and no size limit, which is a real gap for a production version of this service.
