# ADR-000 — Fixed-width, dual-encoding order file ingestion

**Status:** accepted
**Date:** 2026-09-10

## Context

The order export (`orders-20260901.txt`) is fixed-width and encoded in
CP1257, not UTF-8. Reading it with `readFileSync(path, "utf8")` does not
throw — it silently decodes multi-byte Latvian characters incorrectly, so
"Bērziņš" would come out as garbled bytes or replacement characters (�)
while the column positions stay intact and the rest of the line still
looks plausible. Nothing in the program would have crashed; the report
would just have been quietly wrong.

The customer master (`customers.csv`) is UTF-8 — a different encoding in
the same integration, because the two systems were built years apart.

Two other traps: the amount field uses a comma as its decimal separator
("45,20"), and line 6 of the file is a truncated record (26 characters
instead of the required 77) that would have thrown an out-of-bounds error
if I sliced it by fixed column positions without checking its length
first.

## Decision

`decodeOrderFile` reads the order file as raw bytes (`Buffer`, no encoding
applied by `readFileSync`) and decodes them explicitly with
`new TextDecoder("windows-1257")`, rather than trusting Node's default
UTF-8 interpretation.

`ingest` checks each line's length against `ORDER_LINE_LENGTH` (77) before
slicing any fields. A line that isn't exactly 77 characters is pushed into
`rejected` with its 1-based line number and a reason string, and the loop
continues rather than throwing — so one bad record doesn't take down the
whole run.

`toDecimalString` converts the comma separator to a period but returns a
string, never a number. `amount` stays a string end-to-end through the
`Order` interface, specifically so trailing zeros ("45.20") and negative
refund amounts ("-250.00") survive without float rounding or truncation.

`parseCustomers` reads the CSV separately as UTF-8, splits on `;`, and
builds a `customerId -> fullName` map. `ingest` then diffs that map's keys
against the customer IDs seen on accepted orders to produce
`unmatchedCustomers`.

## Alternatives considered

I considered adding `iconv-lite` for the CP1257 decoding, since it's the
more commonly reached-for tool for legacy encodings. I rejected it because
the assignment rules forbid new dependencies, and because `TextDecoder`
already supports the "windows-1257" label natively — the dependency would
have added nothing except an extra thing to maintain.

I also considered storing `amount` as a `number` and formatting it back to
a fixed-decimal string on output. I rejected this because the conversion
to `number` is exactly where the data loss happens — `parseFloat("45,20")`
→ `45.2` loses the trailing zero, and `parseFloat("7800,00")` → `7800`
loses it entirely. Keeping it a string the whole way through avoids ever
passing the value through float arithmetic.

## Consequences

This makes the code brittle to any layout change on the upstream side. If
the exporting system adds a field in the middle of the record, every
column position after it shifts, and my code will silently slice the
wrong bytes into the wrong fields rather than failing loudly — this is a
real risk for a five-year-lifetime integration. A customer name longer
than 32 characters would be truncated by the fixed-width slice with no
warning at all.

If the file arrives UTF-8-encoded by mistake one day, `TextDecoder`
won't throw either — CP1257 and UTF-8 overlap for plain ASCII characters,
so only the diacritic-containing names would come out wrong, and it would
look like the same "quietly incorrect" failure this whole assignment was
built to teach me to watch for.

The cost I accepted: this ingestion has no defense against a layout
change, only against malformed record length. A longer-lived version of
this integration would need either a schema version marker in the file,
or (better) asking the upstream team to move to a self-describing format
like JSON or CSV with a header row, so field identity doesn't depend on
byte position at all.
