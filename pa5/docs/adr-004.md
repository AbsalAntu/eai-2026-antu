# ADR-004 — Header-carried correlation id, file-backed dedup, and return-routed replay

**Status:** accepted
**Date:** 2026-10-26

## Context

An order has to reach payment, inventory and notification, and any of them can fail. Three things made me decide something concrete.

The correlation id. The canonical schema has `additionalProperties: false`, so I could not add a `correlationId` field to the order body. AMQP also has its own `properties.correlationId`, which is a different thing from `properties.headers`. The scaffold and the tests read `headers.correlationId`, so that is where it lives.

The retry path. A failed message is nacked without requeue, waits in a retry queue, and returns to its own consumer queue. `getRetryCount` counts only `x-death` entries with reason `rejected`, because one retry cycle dead-letters a message twice.

My own mistake. After my first rebuild, tests 5, 9 and 10 failed. Test 9 said "expected 1 to be 3", then "expected 2 to be 3" after I fixed payment. The build log showed `COPY src` as `CACHED` for payment and inventory, so both containers were still running the scaffold that always throws. Test 4 (DLQ fills) passed only because a service that always fails fills the DLQ. After that I checked for `CACHED` in the build log every time.

## Decision

`order-service` generates the id with `crypto.randomUUID()` and publishes the order unchanged to `orders.exchange` with `headers: { correlationId }` and `persistent: true`. It keeps the order in a `Map` keyed by that id.

Each consumer (`payment-service`, `inventory-service`, `notification-service`) parses the body inside the `try` block. A `SyntaxError` or a missing `correlationId` header (my `PermanentError`) is permanent. It is published to `orders.invalid.exchange` with the original bytes and headers, then acked. Everything else is temporary and goes through the provided retry/DLQ block, which I did not change. The DLQ publish keeps `originQueue` in the headers. `MAX_RETRIES` defaults to 3 and the simulated failure comes from `*_FAIL_RATE`, read with `??` so that 0 stays 0.

`notification-service` uses the correlation id as the idempotency key. On every message it reads `/data/processed-ids.json`. If the id is there, it acks and logs "duplicate skipped". Otherwise it appends one line to `/data/notification.log`, adds the id, rewrites the file, publishes the result and acks.

`POST /dlq/replay` takes messages one at a time with `channel.get("orders.dlq")`. It republishes the original bytes to `orders.return.exchange` with `originQueue` as the routing key and `withoutRetryHistory(headers)` as headers. It acks only after publishing. A message without `originQueue` is requeued and the loop stops, so it cannot spin.

## Alternatives considered

**AMQP `properties.correlationId`.** It is the standard place. I rejected it because the scaffold and tests read the header, and mixing the two would break tracing in the other services. The cost of choosing it was changing every consumer and every test helper.

**An in-memory `Set` for dedup.** The visible test passes with it, but the set is empty after `docker compose restart notification-service`. A redelivered order would then be logged a second time. A file costs one disk read per message.

**Replaying through `orders.exchange`.** The fanout would send the message to all three consumers. Inventory would process an order twice just because payment failed. Return routing costs one extra exchange and depends on `originQueue` being present.

**One shared errors queue.** It would mix messages that can be replayed with messages that never can. Two channels cost an extra declaration in every service.

## Consequences

Easier: one failing consumer never causes work in the other two. A bad message leaves the retry path immediately instead of waiting out three attempts.

Harder: every consumer must carry the `correlationId` header forward. A future consumer that forgets it breaks tracing for that order. A message without the header is classed as permanent and goes to `orders.invalid`.

What breaks first: if inventory is down for longer than three retry cycles, its message goes to the DLQ. Payment and notification have already succeeded, and nothing tells them. The order stays half-processed until someone calls replay. If the cause is still there, the replay fails three more times and the message returns to the DLQ.

Accepted costs:
- **Dedup gap:** notification writes the log line before it saves the id. A crash between the two would log the order twice on redelivery. I accepted that over losing a notification.
- **Replicas:** two notification replicas would race on the dedup file.
- **In-memory orders:** `order-service` keeps orders in memory, so `GET /orders/:id` returns 404 after a restart.
