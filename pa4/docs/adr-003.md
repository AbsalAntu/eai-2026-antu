# ADR-003 — Allow-list translators with API-priced, string-formatted money

**Status:** accepted
**Date:** 2026-10-12

## Context

Mapping the formats. A single `<LineItem>` in the B2B file parses as an object, not an array, so `translateB2B` wraps it with `Array.isArray` before it maps the lines. The file is CP1257, so `decodeB2BXmlBytes` decodes it with `TextDecoder("windows-1257")` before parsing. The three sources also disagree on product ids. Mobile ids need a `PROD-` prefix, and B2B ids arrive with `SKU-`.

Enriching from pricing. `enrichFromPricing` turns a 404 into `UNKNOWN_PRODUCT` and any other failure into `PRICING_API_ERROR` with the HTTP status. `enrichItems` then adds a warning that names the product and keeps pricing the other lines. The pricing API returns a number. The B2B file also carries a `<UnitListPrice>`, which is decorative and must not be used.

Removing payment data. Every source carries it, in a different place. Web nests it in `customer.payment` with card number, holder and expiry. Mobile sends three flat fields, `pm`, `pan` and `pexp`. B2B keeps `PaymentDetails` inside the customer block. No translator copies any of them.

## Decision

Each source has its own translator: `translateWeb`, `translateMobile` and `translateB2B`. Each builds the canonical order field by field from an allow-list, so payment data is dropped because it is never copied.

`normalizeProductId` maps each source's id format to the pricing API's. `enrichFromPricing` calls the API for one product. `enrichItems` runs it for every line and collects warnings.

Money: `toDecimalAmount` formats the API number with `toFixed(2)`. It does no arithmetic. This is why `4.5` becomes `"4.50"` and not `"4.5"`.

Unpriceable items: an unknown product (404) or a pricing error becomes a warning that names the product. The item is left out. The other items are still priced. No item gets `0.00`.

Status values: `mapMobileStatus` and `mapB2BStatus` throw on an unknown value, because a guessed status would put wrong data into the order.

## Alternatives considered

**Integer cents.** It avoids float formatting. I rejected it because the canonical schema uses decimal strings. Choosing it would mean converting at both ends and changing the schema, which I do not own.

**Fail the whole order when one price fails.** It is simpler. I rejected it because one bad product would block every other line. It would also hide which line failed.

**Cache prices.** It would cut calls. I rejected it because a cached price can be wrong after the catalog changes, and a test changes a price at runtime. The cost I avoided is stale money.

## Consequences

Easier: payment data cannot leak by default, and each source can change on its own.

Harder: all three translators build the order by hand. If the canonical schema gains a required field, all three break at once.

Breaks first: a fourth source with a new product-id format needs a new branch in `normalizeProductId`.

Accepted cost: pricing is one sequential HTTP call per line, with no cache and no timeout. A slow pricing API makes the whole translation slow. I accepted this to keep the code simple.
