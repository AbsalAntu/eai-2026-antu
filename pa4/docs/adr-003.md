# ADR-003 — Allow-list translators into the canonical order model

**Status:** accepted
**Date:** 2026-10-12

## Context

The three sources disagreed on almost everything except that they were orders. The B2B partner sends EDI-style XML in CP1257: the prolog declares `encoding="windows-1257"`, so the bytes have to be decoded with `TextDecoder("windows-1257")` before parsing, or non-ASCII characters are silently corrupted. Its status is an uppercase string ("NEW"), which `mapB2BStatus` lowercases into the canonical `OrderStatus`. Mobile sends status as an integer enum (1 to 4), which `mapMobileStatus` maps to new, processing, shipped or delivered, and its address is one comma-separated string. Parsing that string needs at least four parts (street, city, postal code, country), and the street is whatever remains, because a street can itself contain ", ". Web already uses the canonical status and currency, so those pass through unchanged and only the source label is set.

Enrichment was the second problem. Every line item is priced through the pricing API at `/pricing/{productId}`. A 200 gives a number that has to go through `toDecimalAmount()` rather than straight into the order. A 404 means an unknown product, and any other non-OK response or a network failure (reported as HTTP 0) is an error. The API can fail per item, so a price of 0 is never an acceptable fallback.

## Decision

Each source gets its own translator that builds the canonical order by hand from an explicit allow-list of fields. Anything not listed is dropped, so data that must not travel cannot leak. Pricing failures do not fail the whole order: an item that cannot be priced is left out of `items` and reported as a warning (`UNKNOWN_PRODUCT` for a 404, a "Pricing API error (HTTP n)" warning for everything else), so the caller can see exactly which lines were not priced. An unknown status code or string is different: it throws, because guessing a status would put wrong data into the canonical order.

## Alternatives considered

- **Generic field-copying mapper plus a deny-list.** Rejected: a new field added by any source would flow through to the canonical order by default, and a leak of data that must not travel would be the failure mode instead of a missing field.
- **One shared translator driven by a per-source mapping table.** Rejected for now: the three sources differ in structure (XML with an encoding, a parsed address string, near-canonical JSON), so a table would still need per-source code, and it would be harder to read and test than three explicit functions.
- **Falling back to a price of 0 or the last known price when pricing fails.** Rejected: it would produce orders that look valid but carry wrong money, which is worse than an explicit warning.

## Consequences

- Pricing makes one sequential HTTP call per line item, with no cache and no timeout, so a slow pricing API makes the whole translation slow.
- The three product-id branches are hardcoded, so a fourth source with another id format needs a new branch.
- If the canonical schema gains a required field, all three translators break at once, since each builds the order by hand.
- An allow-list is safe against leaking data and brittle against schema change.
- If the canonical model had to outlive this course, I would add per-call timeouts and bounded parallel pricing requests, put the product-id normalisation behind one shared function with a lookup table, and generate the translators' required fields from the canonical schema so a new required field fails at compile time in one place instead of three.
