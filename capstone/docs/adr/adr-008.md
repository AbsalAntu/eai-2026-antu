# ADR-008 — Three dedup layers, each catching a repeat the others cannot

**Status:** accepted
**Date:** 2026-11-22

## Context

One order can become two in four places. A client repeats a `POST /orders` because it did not see the answer. A client submits the same order again as a new request, with a new key. The broker redelivers a message that was not acked. The orchestrator repeats a call to a provider, in the retry path or after an unknown outcome. Each is a different failure, so one check cannot cover all of them.

I hit two of them while testing. With payment answering `503` twice, the saga ran three attempts, and payment still held exactly one charge. With the same order submitted twice under two keys, both submissions were accepted by intake, and only the first one ran.

## Decision

**Layer 1, the intake Idempotency-Key.** It lives in `/data/idempotency-store.json` on intake, written atomically. A record holds the SHA-256 of the raw body, the state (`in_flight` or `done`) and the response. The same key and the same bytes get the stored answer and publish nothing. A different body under the same key is `409 idempotency_payload_mismatch`. A request that is still running is `409 idempotency_conflict`. The check and the `in_flight` write have no `await` between them in `intake/server.ts`, so two parallel requests cannot both pass. A request that fails with a `400` or a `503` keeps no record, so the key is free for a retry.
*Only this layer catches:* a client that repeats a request after a lost answer. I checked that the same key and body returned the same `correlationId` before and after a restart and a `docker kill`, and the order had one trace.

**Layer 2, the saga business key.** It lives in `businessKeys` in `/data/saga-store.json` on the orchestrator: `source:orderId` maps to the first `correlationId`. A second order with the same business key and a different `correlationId` becomes `duplicate` with `duplicateOf`. No step runs. The check is in `handle` in `orchestrator/saga.ts`.
*Only this layer catches:* the same order sent again under a new key. Intake cannot see it, because a new key is a new request. I ran this: both submissions were accepted, the second ended `duplicate`, and payment held one charge.

**Layer 3, the provider keys.** Payment gets `authorize:<businessKey>` and `refund:<businessKey>`, and inventory gets `reserve:` and `release:`, from `callForward` and `callUndo` in `orchestrator/steps.ts`. The providers store the answer for a key that already had an effect, and return it again with no new effect. Retries in the first-step retry path repeat the same key.
*Only this layer catches:* a repeated call to the provider itself, which the other two layers never see. When payment failed twice and then answered, the order completed and payment showed one charge, with the key `authorize:web:<orderId>`. I did not run the case where the provider performs the charge and then fails the call (`effectThenFail`), so that case rests on the mock's documented behaviour and the same key.

**Notices.** The notifier keeps a persisted set of correlation ids in `/data/processed-ids.json`. It checks the set before it sends, and records the id after a successful send (`notifier/server.ts`). A redelivered outcome event sends nothing.

## Alternatives considered

**One layer.** Only the client key, or only the business key. The client key alone cannot see the same order under a new key. The business key alone does not stop a client that repeats a request from being accepted and published twice, and it does nothing about a repeated call to a provider. Each layer answers a repeat at a different place, so removing one reopens a failure I observed.

**Dedupe on the correlationId only.** The `correlationId` is generated by intake for each accepted submission, so the same order sent twice has two of them. It would catch a redelivery, which the saga already handles by state, and miss the duplicate submission entirely.

**An idempotency key on the notification call.** It would make the notice exactly-once in effect. The notification provider offers no such key, so the key would be ignored. I would only have the appearance of a guarantee. I rejected it and made the notice at-least-once openly.

**Hash the parsed order, not the raw bytes, at intake.** It would treat two bodies that differ only in whitespace as the same order. I rejected it because the brief defines "the same body" as the same bytes, and a canonical form would need its own rules for XML in two encodings.

## Consequences

**Why notices are at-least-once and a charge is not.** A duplicate notice costs a customer one extra message. A duplicate charge costs them money and a refund. The provider keys make a charge exactly-once in effect. For notices I accepted the weaker guarantee. If the provider sent a notice and the call then failed or timed out, a retry or a replay sends a second one, because the id is recorded only after a send that succeeded.

**What the layers still cannot prevent.**
- **A customer who re-orders after a decline.** The business key holds in every state of the first order. From the code, `businessKeys` is set when the first order is consumed and never released, so a resubmission with the same `orderId` becomes `duplicate` of a `failed` order. I ran the duplicate against a completed order, not a declined one. The customer needs a new order id. That is correct for a charge and unkind for a retry after a decline, and I accepted it.
- **Stores that only grow.** The idempotency store and the business-key index are never pruned. A long-running system would need an expiry, and I did not build one.
- **A shipment after a timeout.** None of the layers can stop a provider that finishes a call after we gave up on it. Shipping had one shipment for an order that ended `compensated`, and it has no undo.
- **A key with a changed body.** A client that fixes a typo and keeps the key gets `409`. That is the safe answer, and the client has to choose a new key.
