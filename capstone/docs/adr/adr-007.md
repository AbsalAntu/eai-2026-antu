# ADR-007 — The saga is started by an event, with the outcome persisted before it is published

**Status:** accepted
**Date:** 2026-11-22

## Context

In PA6 a client called `POST /checkout` and held the connection open while the saga ran. When I killed the PA6 orchestrator mid-saga, the client got no answer, and the key stayed `in_progress` for ever: the same request with the same key returned `409 idempotency_conflict`. The saga's state lived in one process and one HTTP request.

In the capstone, intake accepts an order and answers `202` as soon as the broker has confirmed the `order.accepted` event. The orchestrator runs the saga from that event, in its own time. The client no longer waits for it, and a crash of the orchestrator no longer loses the order, because the order is a persistent message in `saga.queue`.

I saw the difference when I killed the orchestrator one second after submitting an order with shipping slowed to 5 s. After `docker start`, the saga was `needs_attention`, listed by `GET /sagas/stuck`. No step ran again, payment and inventory each showed one effect, and the message the dead process never acked came back and was handled.

## Decision

**The saga starts from `saga.queue`.** The consumer is `onMessage` in `orchestrator/saga.ts`. It parses the body inside `try`. A body that is not JSON, not a canonical order, or without a `correlationId` header is quarantined to `orders.invalid` and acked.

**Persist, then publish, then ack.** `recordOutcome` in `orchestrator/state.ts` writes the saga's new state and its outcome event into `/data/saga-store.json` in one atomic write (a temporary file renamed over the old one). Then `sendAndAck` in `orchestrator/run.ts` publishes the event with a broker confirm. Only then does it ack the message. If the publish fails, it puts the message back (`nack` with requeue), so a redelivery republishes the stored outcome.

**A crash between the write and the publish.** The message was never acked, so the broker delivers it again. The consumer finds a saga that already has an outcome, writes a `saga.dedupe` hop with status `skipped`, and republishes the stored envelope with a new `messageId`. No step runs. The outcome event is therefore at-least-once, and every consumer of `orders.outcome` has to tolerate a repeat.

**Prefetch and concurrency.** The shared runtime sets `prefetch(10)`. The orchestrator takes a slot from a counting semaphore (`acquire` in `saga.ts`) before it handles a message, so at most `SAGA_CONCURRENCY` (5) sagas run at once. The other messages the consumer holds wait, unacked, for a slot. With five slow sagas, up to five more sit unacked in the consumer, and `GET /ops/metrics` shows them as `unacked`, not `ready`.

**How `GET /orders` learns the state.** Intake binds its own queue, `intake.state.queue`, to `orders.outcome` with `#`. `makeFollower` in `intake/follow.ts` applies each event only if the move is allowed from the current state (the `ALLOWED` table). `accepted` may become any state, a terminal state allows nothing, and `needs_attention` and `compensation_failed` may only become `compensated` or stay as they are. So a late or repeated event can never move a terminal state backwards.
