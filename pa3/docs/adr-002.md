# ADR-002 — Correlation, idle timeout, partial-result shape, and duplicate handling in the aggregator

**Status:** accepted
**Date:** 2026-10-05

## Context

The router splits one order into N independent messages, each travelling to one
of three queues (physical/digital/subscription), processed by three separate
worker processes running at different speeds. The aggregator has no way to know
in advance how many of those N results will actually arrive, in what order, or
whether a worker is simply slow versus genuinely down. It has to reconstruct
"this order is done" from a stream of unordered, possibly-duplicated,
possibly-incomplete results, without blocking forever on a worker that never
answers. None of this was obvious going in: the first version I wrote counted
received messages with a plain integer counter, which looked correct until I
thought through what a RabbitMQ redelivery after a late ack would do to that
count -- that's what forced the actual data structure decision below.

## Decision

**Correlation:** the router copies the order's `orderId` into every split
item's `orderId` and `correlationId` fields (both the same value), and stamps
the order's original `totalItems` onto every item message. The aggregator uses
`orderId` as the key into its in-flight dict and uses the `totalItems` value
carried on the *first* result it sees for that order to know how many items to
wait for. If a worker stripped or renamed `orderId`, the aggregator would never
be able to group that result with its siblings, and it would sit as an
unreachable entry until the sweep timed it out as "partial" with that one item
silently missing -- nothing would crash, but the order would be reported
incomplete.

**Timeout:** `aggregate_result` resets `lastActivity` on the order's in-flight
entry every time a result comes in. A background thread (`sweep_timeouts`)
runs every `SWEEP_INTERVAL_SECONDS` (1s) and emits a `"partial"` completion for
any order whose `lastActivity` is more than `IDLE_TIMEOUT_SECONDS` in the past.
The test harness pins this to 5s; in production I would run it closer to
15-30s, set from the p99 latency of the slowest worker (the physical-item
worker, since shipping-adjacent processing is the one most likely to call out
to something external) plus margin, re-measured periodically rather than fixed
once.

**Partial result shape:** `missingItemIndexes` is computed as the set
difference between `range(totalItems)` and the keys actually received, and is
always present (empty list on `"complete"`, non-empty on `"partial"`). A bare
`"status": "partial"` with no detail would tell a downstream consumer nothing
actionable; naming the missing indexes is what lets whatever reads
`orders.complete` retry exactly the items that didn't show up instead of
re-submitting the whole order.

**Duplicates:** results are stored in `entry["results"]`, a dict keyed by
`itemIndex`, not a list or a counter. A redelivered duplicate for the same
`itemIndex` simply overwrites the existing entry at that key -- `len()` of the
dict is always the count of *distinct* items received, so a late-acked,
redelivered message cannot inflate the count or trigger early completion.

## Alternatives considered

A fixed deadline measured from order arrival (rather than an idle timeout)
was the obvious first design and is what I initially expected to need. I
rejected it once I considered a 50-item order: if items are still trickling
in from healthy workers at item 48 when a fixed 5-second-from-arrival deadline
expires, the order gets flagged partial even though nothing has actually
failed -- the aggregator would be punishing a large order for being large.
Resetting the clock on every result received keeps the signal honest: it only
expires when the order has genuinely gone quiet.

I also considered counting received items with a plain `int` instead of a
dict keyed by `itemIndex`. I rejected this directly because of the duplicate
requirement in the spec -- an `int` counter has no way to distinguish "a new
item arrived" from "an already-seen item was redelivered," so a single
duplicate would inflate the count and could trigger a false "complete" with
one of the original items still genuinely missing.

## Consequences

State lives entirely in a Python dict (`in_flight`) inside the single
aggregator process, guarded by one `threading.Lock`. This is easy to reason
about and fast enough for this scale, but it means aggregation state is not
durable: if the aggregator container restarts mid-order, every order it was
tracking is silently lost -- no partial, no complete, nothing published for
it, and the items already acked off `orders.results` are gone too. That's an
accepted cost here, since PA3 has no restart test, but it's the first thing
I'd fix before production: either persisting in-flight state to Redis/a
database, or not acking an item result until its order is either complete or
explicitly dropped by the timeout.

The single global `lock` is also a scaling ceiling. At ten times the current
throughput, every aggregator worker thread serializes on that one lock for
every single result message, even for unrelated orders -- the fix would be
sharding the lock (or the whole in-flight map) by `orderId` hash, or moving
aggregation state out of process memory entirely so multiple aggregator
replicas could share the work.
